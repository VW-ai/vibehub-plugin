## Problem Statement

The owner needs a personal Ticket control plane that can capture an intention through Claude Code or Codex, turn it into a durable Ticket draft, and organize it by project without forcing every Ticket into a project hierarchy. Today the Private pilot registry preserves work across branches, worktrees, pull requests, Slack threads, and Agent tasks, but requires several manually synchronized Markdown projections. The new product should make one Ticket file authoritative, derive Inbox and Project views automatically, and hand selected work to the existing repository-local VibeHub cycle.

This is not a second project-management system and not a replacement for the VibeHub Plugin. It is the personal, cross-project intake and routing surface that the current repository-local Plugin does not yet provide.

## What Makes This Cool

The user can tell either Claude or Codex, “给 Private pilot 建一个 Ticket” or “把这个想法先放进 VibeHub 项目,” and the same Ticket appears immediately in one personal Inbox. The Ticket can remain unassigned, be viewed under one or more Projects, or be explicitly handed to a target repository. Conversation is disposable; the captured Ticket is not.

The product stays deliberately small: it organizes intentions and produces bounded Ticket drafts. It does not pretend that a generated draft is executing, finished, merged, or production-proven.

## Constraints

- Create a new sibling code repository, tentatively `vibehub-personal`; do not place the cross-project application inside the repository-local Plugin runtime.
- Keep VibeHub as one product and one Ticket language. Personal Hub may define an intake envelope, but it must not fork the canonical executable Ticket contract.
- Store personal Ticket data outside the application repository in a configurable local directory or private Git repository.
- Integrate with Claude Code and Codex through shared Skills plus a deterministic local CLI. Do not require direct provider API keys or embed an Agent runtime in MVP.
- Keep the MVP local-first and single-user. No accounts, cloud synchronization, multi-user permissions, mobile client, or organization workflow administration.
- Project is an optional view and routing reference, not a mandatory parent. An Inbox Ticket may have zero Projects; cross-project work may reference more than one.
- Personal Hub owns intake state only. Target repositories remain authoritative for executable VibeHub Ticket, Evidence, Outcome, delivery, and closeout state.
- No automatic or silent write into a target repository. Handoff is explicit, previewable, and attributable.
- One Ticket file is canonical. Inbox, Project, Active, and Archive pages are derived projections rather than separately edited documents.
- Preserve private Private pilot source material. The code repository must contain fixtures with synthetic or redacted content only.

## Premises

1. The immediate pain is durable capture, AI-assisted Ticket generation, and project-oriented retrieval—not automated execution orchestration.
2. Claude Code and Codex are replaceable producers of the same deterministic local write contract.
3. A personal Ticket draft and an executable repository Ticket are different maturity stages of one idea; crossing that boundary requires an explicit handoff.
4. Plain files remain the durable authority because they are inspectable, diffable, recoverable, and compatible with the existing VibeHub product model.
5. The Private pilot registry is strong domain evidence but should be migrated into one-record-per-file data, not reproduced as another collection of manually synchronized indexes.

## Approaches Considered

### Approach A: Expand the existing VibeHub Plugin repository

Add a global Project catalog, personal Inbox, cross-repository writes, and a persistent application surface directly to the existing Plugin. Rejected because it couples a new cross-project application lifecycle to the current repository-local release and conflicts with the current single-Workspace V1 boundary.

### Approach B: Separate Personal Hub, shared VibeHub contract

Build a new sibling repository for the application and its dual-host capture Skills. Keep personal data in a separate configurable directory. Use an explicit adapter to transform an approved personal draft into a target repository's canonical VibeHub Ticket.

This is the selected architecture.

### Approach C: Markdown registry plus two prompt-only Skills

Create only a private Git directory and prompt instructions for Claude and Codex. This ships fastest, but without a deterministic CLI, atomic writes, schema validation, or derived projections it recreates the manual consistency problems visible in the Private pilot registry. The useful part of this approach becomes the first vertical slice of Approach B rather than a separate final architecture.

## Recommended Approach

### Repository and data boundary

Use this initial layout:

```text
<workspace>/VibeHub/
├── vibehub-plugin/                 # Existing project-local protocol and lifecycle
└── vibehub-personal/               # New application code

<configurable private data root>/
├── store.yaml
├── projects/
│   └── <project-id>.yaml
├── tickets/
│   └── <personal-ticket-id>.yaml
└── handoffs/
    └── <handoff-id>.yaml
```

Archived Tickets remain under `tickets/`; Archive is always a derived view. Setup writes one OS user-config pointer—overridable by `VIBEHUB_PERSONAL_CONFIG`—whose strict v1 schema contains only `kind: personal_hub_config`, `schema_version: 1`, and the absolute `data_root`. The root-local `store.yaml` is not a second preference layer; it is a strict format marker containing `kind: personal_ticket_store`, `schema_version: 1`, and `format_version: 1`. The data root can itself be a private Git repository, but the application never assumes Git is present and never auto-commits.

Delivery is staged deliberately:

- **MVP:** schemas, deterministic CLI, project registry, Claude/Codex capture Skills, and derived JSON/text Inbox and Project views.
- **Milestone 2:** read-only local Web list/detail view after MVP dogfood stabilizes file and query contracts.
- **Milestone 3:** explicit repository handoff and the five-record Private pilot.

The MVP is useful before either Web or handoff exists: it replaces manual multi-file capture with one validated record and lets both Agent hosts query the same personal Inbox.

### Product objects

#### Project Reference

A Project Reference is a personal view and routing record, not the Ticket's parent.

| Field | Type and rule |
| --- | --- |
| `schema_version` | Integer constant `1` |
| `kind` | Constant `personal_project` |
| `project_id` | Globally unique lowercase kebab ID matching `^[a-z0-9]+(?:-[a-z0-9]+)*$` |
| `name` | Non-empty display string |
| `aliases` | Unique case-insensitive strings across all Projects |
| `repo_path` | Optional absolute path; resolved and verified only when an adapter operation needs it |
| `adapter` | `vibehub` or `none` |
| `playbook_refs` | Ordered array of typed local or URL References; empty is valid |
| `created_at`, `updated_at` | RFC 3339 UTC timestamps |
| `revision` | Positive monotonic integer |

No tokens, provider secrets, or copied repository Context belong in this file.

#### Personal Ticket Draft

| Field | Type and rule |
| --- | --- |
| `schema_version` | Integer constant `1` |
| `kind` | Constant `personal_ticket` |
| `personal_ticket_id` | Immutable globally unique lowercase kebab ID |
| `title` | Non-empty display string, maximum 160 Unicode scalar values |
| `desired_outcome` | Optional in `inbox`; required and non-empty in `draft` and `ready`; an archived Ticket retains whether it was present before archive; this is not a VibeHub Outcome record |
| `state` | `inbox`, `draft`, `ready`, or `archived` |
| `project_refs` | Unique ordered Project IDs; empty and multiple values are valid |
| `source_refs` | Typed references to the exact user-provided source, host task, URL, or local file |
| `source_excerpt` | Optional current-request excerpt captured only as described by the source policy below |
| `acceptance` | Ordered criteria; empty is valid until `ready` |
| `next_gate` | Optional bounded next action; used by imported operational records |
| `external_keys` | Typed `(system, key)` pairs such as `(private-pilot, DEMO-001)`, unique per system |
| `external_delivery_refs` | Non-authoritative typed URLs/commits/status labels retained for imported work |
| `generation_host` | `claude-code`, `codex`, `user`, or `import` |
| `last_archive` | Optional typed `(reason, archived_at, from_state)` record; required while state is `archived` and retained after reopen |
| `created_at`, `updated_at` | RFC 3339 UTC timestamps |
| `revision` | Positive monotonic integer |

Optional display or imported identifiers such as `DEMO-001` are stored as external keys rather than used as global identity. This avoids collisions between projects while preserving the identifier users recognize.

Personal state deliberately excludes `running`, `merged`, `production-proven`, Evidence, and Outcome. Those belong to a materialized VibeHub Ticket or an external system reference.

All record schemas reject unknown fields. The contract-and-fixtures Ticket checks in JSON Schemas plus valid and invalid canonical fixtures for MVP Project and Ticket objects before data-core implementation starts. The Milestone 3 handoff Ticket adds its journal schema and fixtures before handoff code.

Example:

```yaml
schema_version: 1
kind: personal_ticket
personal_ticket_id: pt-20260820-private-pilot-upcoming-calls
title: Clarify Upcoming Calls scope
desired_outcome: Define the exact account and time boundary before implementation.
state: draft
project_refs: [private-pilot]
source_refs:
  - kind: local_file
    ref: <private-source>/DEMO-008.md
acceptance: []
next_gate: Audit one unfamiliar row with its account and calendar provenance.
external_keys:
  - system: private-pilot
    key: DEMO-008
external_delivery_refs: []
generation_host: import
created_at: 2026-08-20T00:00:00Z
updated_at: 2026-08-20T00:00:00Z
revision: 1
```

### Lifecycle and projections

Project assignment is independent of lifecycle. Assigning or removing a Project never changes Ticket state.

| From | To | Rule |
| --- | --- | --- |
| new | `inbox` | Capture may contain only title and source fields |
| `inbox` | `draft` | `desired_outcome` is present |
| `draft` | `ready` | Desired outcome and at least one acceptance criterion pass ready validation |
| `ready` | `draft` | Any readiness-affecting field change invalidates readiness |
| `inbox` | `archived` | Explicit command with a non-empty reason; `last_archive.from_state` is `inbox` |
| `draft` | `archived` | Explicit command with a non-empty reason; `last_archive.from_state` is `draft` |
| `ready` | `archived` | Explicit command with a non-empty reason; `last_archive.from_state` is `ready` |
| `archived` | `inbox` | Explicit reopen when `desired_outcome` is absent |
| `archived` | `draft` | Explicit reopen when `desired_outcome` exists; reopen never restores `ready` automatically |

Derived projections are exact:

- **Inbox:** `state == inbox`.
- **Drafts:** `state == draft`.
- **Ready:** `state == ready`.
- **Active:** `state` is one of `inbox`, `draft`, or `ready`.
- **Project:** `project_refs` contains the selected Project ID, independent of state.
- **Unassigned:** `project_refs` is empty.
- **Archive:** `state == archived`.
- **Handed off:** at least one handoff journal with this `source_ticket_id` has status `materialized`; this is not a Ticket lifecycle state.

Ready validation requires `desired_outcome`, at least one non-empty acceptance criterion, valid references, and no schema or Diagnostics errors. It does not require a Project. Handoff validation additionally requires one explicitly selected registered Project with `adapter: vibehub`, a live repository path, and a compatible VibeHub format.

The fields `title`, `desired_outcome`, `source_refs`, `source_excerpt`, `acceptance`, and `next_gate` are readiness-affecting. Updating any of them moves `ready` to `draft`. Project assignment, external-key/delivery bookkeeping, timestamps, and revision are orthogonal and do not change lifecycle state.

The CLI does not claim built-in revision history. `revision` is a concurrency token. If the configured data root is a Git repository, Git may provide history; otherwise Ticket detail shows only the current revision and immutable handoff receipts.

### Source capture policy

Invoking the capture Skill authorizes capture of the current user request only, not the surrounding transcript. By default the Skill stores a host task/thread Reference and the user-supplied URLs or files. It stores `source_excerpt` only when the preview shows the excerpt or the user explicitly asks to preserve the wording. No previous conversation turns, tool output, repository scan, or background transcript are harvested.

#### Shared subobjects

The contract Ticket must encode these strict shapes in the checked-in JSON Schemas; implementations may not invent additional fields:

| Object | Required shape |
| --- | --- |
| Reference | `{ kind: local_file | url | host_task | git_commit, ref: non-empty string, label?: string }` |
| Acceptance | `{ acceptance_id: kebab-id, criterion: non-empty string }` |
| External key | `{ system: kebab-id, key: non-empty string }` |
| External delivery reference | `{ kind: pull_request | commit | external_status, ref: non-empty string, state?: string, observed_at: RFC3339 }` |
| Structured error | `{ code: stable-kebab-code, message: string, details?: object }` |
| Validation receipt | `{ validator: vibehub, project_format: 2, ticket_schema: 2, target_path: relative-path, payload_sha256: hex, checked_at: RFC3339 }` |

The pair `(system, key)` is globally unique across all Personal Tickets. A collision makes capture a confirmation-required update/merge decision; the CLI never creates a second record automatically.

Every canonical filename must equal its immutable record ID plus `.yaml`. A basename/ID mismatch or duplicate ID anywhere in the data root is a Diagnostics error and blocks mutation of the affected records.

#### Handoff Record

A handoff records an explicit attempt to materialize one approved snapshot into one target repository.

| Field | Type and rule |
| --- | --- |
| `schema_version`, `kind` | Constant `1` and `personal_handoff` |
| `handoff_id` | Immutable globally unique kebab ID; filename must be `<handoff-id>.yaml` |
| `source_ticket_id`, `source_revision`, `source_content_hash` | Immutable identity of the approved Personal Ticket snapshot |
| `project_id` | Immutable selected Project |
| `target_repository` | Immutable preview identity: registered real path, Git common-dir real path, remote URL when present, and preview HEAD |
| `target_ticket_id`, `target_relative_path` | Immutable proposed VibeHub Ticket identity and deterministic path |
| `compiled_ticket_yaml`, `payload_sha256` | Immutable approved payload encoded as UTF-8, LF-only, no BOM; SHA-256 is computed over those exact encoded bytes |
| `idempotency_key` | Immutable hash of handoff ID plus payload hash |
| `actor` | `claude-code`, `codex`, or `user` |
| `status` | `previewed`, `materialized`, or `failed` |
| `validation_receipt` | Required only when `materialized` |
| `error`, `last_reconciled_at` | Structured error and timestamp when incomplete or retried |
| `created_at`, `updated_at`, `revision` | RFC 3339 UTC timestamps and positive monotonic revision |

Allowed transitions are `new → previewed`, `previewed → materialized|failed`, and `failed → materialized|failed` through explicit retry/reconciliation. Immutable fields never change after `previewed` is written.

A handoff never silently changes the source Personal Ticket lifecycle. `materialized` means the exact target path exists with the expected content hash and target-repository VibeHub validation succeeded.

Milestone 3 uses a journaled, idempotent sequence owned by the host Skill:

1. `handoff preview` validates a `ready` source Ticket, detects target VibeHub format `2` / Ticket schema `2`, stores the exact compiled YAML snapshot, and writes one `previewed` handoff journal.
2. The Skill shows the exact target repository, path, and compiled Ticket and requires explicit confirmation.
3. Confirmation names the handoff ID and payload hash. The Skill materializes that approved snapshot even if the source Personal Ticket later changes; a new preview is required for different bytes.
4. The Skill revalidates the repository identity and target path immediately before writing, delegates to its installed VibeHub Ticket Plan/Validate workflow, and refuses to overwrite a different existing Ticket.
5. The Skill calls `handoff record-materialized` with the validation receipt.
6. If target creation succeeded but personal recording failed, the stable handoff ID and deterministic target path allow `handoff reconcile` to finish the journal without creating a duplicate. Reconcile requires the host Skill to rerun repository-local validation and provide a fresh receipt; the CLI verifies the target bytes, path, and payload hash but never launches the validator itself.

Personal Tickets do not duplicate handoff IDs. The Handed-off projection derives journals by `source_ticket_id`, so journal repair cannot disagree with a Ticket-side index.

The CLI and Web application never launch an Agent or pretend to own repository-local Plan/Validate. The host Skill owns orchestration; the CLI owns personal data and receipts.

### Write contract and concurrency

All supported mutations go through one CLI used by both Agent Skills and later by the Web application. MVP commands:

```text
vh-personal project add|get|list|update|remove
vh-personal ticket capture|get|list|update|archive|reopen
vh-personal validate
vh-personal repair lock
```

Milestone 3 adds:

```text
vh-personal handoff preview|record-materialized|record-failed|reconcile
vh-personal import private-pilot --dry-run|--apply
```

Commands accept structured JSON input and emit one structured JSON envelope to stdout; diagnostics go to stderr. Stable exit codes are `0` success, `2` validation, `3` revision conflict, `4` not found, `5` permission/path boundary, `6` VibeHub compatibility, and `7` incomplete handoff requiring reconciliation.

Every update supplies `expected_revision` and `expected_content_hash`. MVP serializes mutations through one data-root interprocess write lock because Project aliases, Project references, external keys, and ID uniqueness are cross-record invariants. While holding it, the CLI rescans affected catalogs, re-reads and revalidates records, checks expectations, writes temporary sibling files, fsyncs them, atomically renames them, and fsyncs parent directories where supported. This favors correctness over write throughput for a single-user product; per-record lock optimization is deferred.

Lock metadata includes host, PID, process-start identity where the platform exposes it, a random owner token, and creation time. Stale locks are never broken merely by age or PID absence. `vh-personal repair lock` verifies that the PID plus process-start identity no longer matches, shows the owner token and affected operation, and requires an explicit repair action.

Manual edits are supported only while no Personal Hub process is writing. On startup and every read, files are rescanned and validated; malformed records appear in Diagnostics and are never silently repaired or overwritten. Filesystem watch events are refresh hints only, never correctness authority.

Project update uses the same revision/hash protocol as Ticket update. MVP refuses Project removal while any Ticket references it; users update those Tickets individually before retrying removal. Alias uniqueness, global external-key uniqueness, filename/ID identity, and reference integrity are validated across the full data root while the data-root lock is held.

IDs and paths are resolved inside the configured data root. Target repository writes are not exposed through a generic path argument; they require a registered Project and a separate handoff operation.

### Claude Code and Codex connection

Ship the same semantic Skills in both plugin formats:

- `vibehub-personal-capture`: turn the current request into a Personal Ticket preview and call the CLI.
- `vibehub-personal-inbox`: list or inspect derived Inbox and Project views.
- `vibehub-personal-handoff`: Milestone 3 only; preview transfer to a registered VibeHub repository and orchestrate its installed VibeHub Ticket Plan/Validate workflow.

The Skills call `vh-personal`; they do not hand-edit YAML. Claude and Codex therefore share validation, conflict handling, and output semantics.

Capture always previews when the Project is unknown or has multiple alias matches, a duplicate external key or highly similar active title exists, the request asks for `ready` without acceptance, or existing data would be updated. A new unambiguous `inbox` capture may write immediately because invoking the Skill is the explicit user action. `--preview` forces no-write behavior; `--confirm <preview-hash>` performs the exact previewed write; non-interactive mode fails rather than guessing when confirmation is required.

MVP does not launch Claude or Codex from an application. The installed host Agent writes through the CLI. A later trusted host bridge can add an in-app “Generate with AI” action without changing storage authority.

### Local Web application (Milestone 2)

The first UI is a local browser application with three primary surfaces:

1. **Inbox** — exactly the Tickets whose lifecycle state is `inbox`, with source policy and generation host visible.
2. **Projects** — the same Ticket files grouped by Project Reference; changing the view never moves or duplicates the Ticket. Unassigned is a separate orthogonal filter.
3. **Ticket detail** — desired outcome, acceptance, source, Projects, current revision, and immutable handoff receipts when they exist.

Dogfood must first prove that CLI text/JSON list and detail projections are sufficient and stable. Only then add a Node 20+ local server bound to loopback and a TypeScript Web client. The server owns validated file access and uses filesystem watching only to request a full rescan. Every read and future write route requires a short-lived capability token, strict `Host` and `Origin` validation, no permissive CORS, and DNS-rebinding regression tests. The browser never receives an arbitrary filesystem API.

The UI is a list/detail product rather than another causal execution graph. The existing Workbench remains the right surface after a Ticket is handed to a repository and gains dependencies, Evidence, and Outcome.

### VibeHub contract sharing (Milestone 3)

MVP ships only the Personal Project and Personal Ticket contracts. Milestone 3 pins VibeHub project format `2` and Ticket schema `2` from one released contract bundle by exact release tag and checksum. The executable Ticket schema is never copied and modified ad hoc. Handoff preview reads the target `.vibehub/version.yaml`; a missing or different format returns exit `6` with the required migration or supported version. Multi-version negotiation is deferred.

The Personal Ticket schema is intentionally an intake envelope. Handoff compilation maps only fields with explicit semantics and fails on missing required acceptance or invalid target references. It does not guess dependencies, Evidence, or completion state.

### Private pilot migration (Milestone 3 pilot)

Use `<private-pilot-source>/my-tickets` as a pilot source, not as a live dual-write system indefinitely.

1. Select five representative records: `INTAKE`, `GATED`, `OPEN`, `DEVELOPED-LOCAL`, and `MERGED-VERIFY`.
2. Import each as one Personal Ticket while preserving its recognized ID, source links, next gate, and current delivery evidence as external references.
3. Compare generated Inbox/Project/Archive projections with the existing Markdown views.
4. Stop after the five-record pilot. Full import and freezing the old registry require a separate owner decision based on dogfood results.

The importer supports `--dry-run` and `--apply`, uses source path plus recognized external key as its idempotency key, reports collisions without overwriting, and can resume after interruption. Historical delivery states remain non-authoritative external references. They are not collapsed into Personal Ticket state and are not reinterpreted as VibeHub Outcome.

### Trust boundaries

- A Milestone 2 Web server binds only to loopback.
- Registered repository paths are canonicalized at preview and revalidated immediately before handoff; moved or deleted repositories fail safely.
- Symlink traversal outside configured roots is rejected.
- Agent writes require schema-valid JSON input, the data-root interprocess write lock, and revision/hash checks.
- Private source content stays in the configured data root.
- No background provider calls, transcript harvesting, implicit repository scan, or automatic target-repository writes occur.

After this design is approved, create the following executable planning graph in the existing VibeHub repository. Permanent implementation begins in the new repository only after the graph's contract and repository boundary Tickets close.

```text
personal-hub-contract-and-fixtures
        ↓
personal-hub-repository-foundation
        ↓
personal-hub-data-core
        ├──────────────────────────────→ personal-hub-private-pilot
        ↓

        ├──────────────────┐
        ↓                  ↓

```

- **Contract and fixtures:** lock Personal Ticket and Project Reference schemas plus synthetic/redacted fixtures; defer executable VibeHub and handoff contracts.
- **Repository foundation:** create the private sibling repository, CI, OS config/data-root boundary, store marker, and Personal contract metadata.
- **Data core:** implement deterministic CLI, validation, atomic writes, revision conflicts, derived queries, and tests.
- **Dual-host capture:** package equivalent Claude Code and Codex Skills that use the CLI; completing this Ticket makes MVP usable.
- **Local Web:** after MVP dogfood, implement read-only Inbox, Projects, Ticket detail, rescan-on-refresh, and honest invalid/conflict states.
- **VibeHub handoff:** pin VibeHub format/schema versions, lock the handoff schema, and implement the host-Skill-owned idempotent journal plus repository-local Ticket Plan/Validate handoff without automatic execution; it does not depend on Web.
- **Private pilot:** after data core, migrate and verify five representative records; it does not depend on Web or handoff, and full import requires another decision.

## Success Criteria

### MVP

- A fresh local setup registers at least two Projects and captures an unassigned Inbox Ticket without touching either repository.
- Claude Code and Codex can each create a schema-valid Ticket through the same CLI; neither Skill hand-edits files.
- Concurrent edits with the same prior revision cause one deterministic conflict and no lost update.
- Inbox and Project views are derived from the same Ticket files and cannot drift through separate manual edits.
- All application fixtures and repository history remain free of private Private pilot content.
- Core schema, state transition, query projection, write-lock/conflict, path-boundary, and both Skill contract tests run in CI.

### Milestone 2

- The read-only Web view shows the same Inbox, Project, Ready, Unassigned, and Archive results as CLI JSON for identical data.
- Watcher loss or coalescing cannot cause incorrect state because every navigation/refresh performs a validated rescan.

### Milestone 3

- A user can preview and explicitly hand one ready Ticket to a registered VibeHub format-2 repository, where repository-local validation succeeds.
- Retrying or reconciling the same handoff cannot create a second target Ticket or overwrite different content.
- Handoff never marks execution, completion, merge, or production proof.
- Five representative Private pilot records retain recognized IDs, sources, next gates, and delivery references after pilot import.

## Distribution Plan

- Start as a private GitHub repository named `vibehub-personal`.
- Require Node.js 20+ and provide one local setup command that chooses the data directory, creates initial configuration, and installs or links the Claude Code and Codex plugin Skills for dogfood.
- GitHub Actions run MVP unit, schema, state, concurrency, path-boundary, and dual-host Skill contract tests on every pull request; Web and handoff gates are added only with their milestones.
- MVP distribution is source checkout plus a pinned lockfile. No npm publication, cloud deployment, auto-update, or public marketplace listing until daily dogfood stabilizes the contracts.
- Release archives and multi-version compatibility are deferred until daily dogfood stabilizes the contracts.

## Open Questions

- Whether the Milestone 2 Web client should use the lightest possible dependency stack or share selected visual components with the VibeHub Workbench. This does not block MVP.
- Whether Personal Hub should eventually own an in-app Agent bridge. MVP intentionally keeps generation in Claude Code/Codex Skills.
- Whether one Personal Ticket handed to multiple repositories should remain one personal coordination object or be split before handoff. Milestone 3 supports one target per handoff and records multiple receipts without claiming cross-repository execution semantics.
